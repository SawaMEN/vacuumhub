# Каталог устройств и аппаратных вариантов (этап 2)

> Реализовано: API, фильтры сайта, форма администратора, атомарный импорт и проверка статуса идентификатора.
> **Подтверждённый аппаратный ID не доказывает совместимость прошивки.** Автоматическая прошивка устройств не реализована.

## Схема

- `manufacturers`: справочник производителей (slug, имя, сайт). Старые `models.brand` сохранены для обратной совместимости и сопоставляются по имени производителя.
- `models`: маркетинговые модели с исходным `device_id` (если есть). Унаследованный `device_id` не считается подтверждённым.
- `model_variants`: конкретные варианты с уникальным `id`, `model_slug`, SKU, регионом, ревизией платы и примечаниями.
- `variant_identifiers`: идентификатор, вид (`hardware_id`, `miot_model`, `sku`, `model_number`, `vendor`), значение, ссылка на источник (HTTPS), статус `verified`/`unverified`.

Для `verified` у `hardware_id` обязательны источник HTTPS, регион и ревизия. Один подтверждённый `hardware_id` не может одновременно принадлежать двум вариантам (без учёта регистра). Смена региона или ревизии автоматически сбрасывает подтверждение старых идентификаторов. Это фиксирует проверку источника администратором, а не криптографическую аутентичность или успешную установку прошивки.

## Публичное API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/manufacturers` | Справочник производителей и число моделей |
| GET | `/api/v1/models` | Каталог и поиск |
| GET | `/api/v1/models/{slug}` | Общие сведения о модели |
| GET | `/api/v1/models/{slug}/variants` | Ревизии и источники идентификаторов |

Параметры `/models`: `q`, `brand`, `region`, `revision`, `identifier`, `verified=0|1`. Фильтры, относящиеся к варианту, применяются к **одному и тому же варианту**, чтобы не выдавать ложное совпадение между разными ревизиями. Поиск ограничен 200 моделями; пагинация запланирована отдельно.

## Административное API

Запросы должны содержать `Authorization: Bearer <ADMIN_API_TOKEN>`.

- `POST /api/v1/admin/manufacturers` с JSON `{ "slug": "brand-id", "name": "Название", "website": "https://example.org" }`.
- `POST /api/v1/admin/models` — создание модели, производитель уже должен быть в справочнике.
- `POST /api/v1/admin/catalog/import` — импорт 1–100 вариантов, до 20 идентификаторов на каждый. Транзакция: либо всё сохраняется, либо ничего. Повторный импорт обновляет вариант по `id` и идентификаторы по `(variant_id,kind,value)`.

Пример (значения вымышленные; не добавляйте этот пример в публичный каталог):

```json
{
  "variants": [
    {
      "id": "example-model-global-board-a",
      "model_slug": "roborock-s5",
      "sku": "EXAMPLE-SKU",
      "region": "global",
      "hardware_revision": "board-A",
      "notes": "Только пример структуры импорта",
      "identifiers": [
        {
          "kind": "hardware_id",
          "value": "EXAMPLE-HW-ID",
          "source_url": "https://example.org/source",
          "verification": "unverified"
        }
      ]
    }
  ]
}
```

```bash
curl --fail-with-body -X POST "https://your-domain.example/api/v1/admin/catalog/import" \
  -H "Authorization: Bearer $ADMIN_API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @catalog.json
```

До изменения базы на работающем VDS создайте резервную копию SQLite и файлового архива. Новые таблицы создаются при старте миграции и не удаляют существующие модели или файлы.

## Что пока не реализовано

Автоматическая проверка реальности ссылок, получение device ID непосредственно из робота, сканирование подписей прошивок, установщик и восстановление устройства. Эти функции нельзя подменять пользовательским флагом `verified`; они запланированы для последующих этапов.
